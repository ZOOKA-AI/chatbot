# Engineer access — issued from code, never from a chat

Everything an outside engineer needs is granted by a script in this repository, so the
grant is reviewable, repeatable and revocable. No credential is ever committed, printed
in a ticket, or pasted into a chat: this repository is public, and a token in a commit is
a published token.

## The four accesses

| Access | Granted by | Held where | Revoked by |
| --- | --- | --- | --- |
| Platform admin in `/admin` | `scripts/admin/platform-role.mjs grant --user-id <uuid> --role admin` | `PlatformRole` row, read on every request | `scripts/admin/platform-role.mjs revoke --user-id <uuid>` |
| Read-only production SQL | `scripts/admin/engineer-access.mjs grant-readonly-db --role engineer_ro` | a Postgres login role | `... revoke-readonly-db --role engineer_ro` |
| Vercel team token | `scripts/admin/engineer-access.mjs grant-vercel-token --name engineer-zooka-ai --days 30` | Vercel account, expires by itself | delete the token in Vercel settings |
| Repository write | `scripts/admin/engineer-access.mjs grant-github-deploy-key --title engineer --key-file ./engineer.pub --read-write` | a deploy key on this repo | `... revoke-github-deploy-key --title engineer` |

The account the admin access hangs on is an ordinary user: sign up at `/login`, then grant
the platform role by user id. Owning a workspace is never enough — the gate reads
`PlatformRole` on every request and fails closed when the table or the row is missing.

## Why a deploy key instead of a collaborator invite

This repository belongs to a personal GitHub account, not an organisation, so GitHub
offers no email invitation for a collaborator. A deploy key needs no invitation and no
account, which is why it is the default. If the repository is ever moved into an
organisation, replace it with a normal collaborator seat.

## Environment the scripts need

Names only; the values live in the owner's secret store and in Vercel, never in this repo.

- `PLATFORM_ROLE_DATABASE_URL` — the database to touch. A production project ref also
  requires `--confirm-production`, so a stray shell cannot promote anyone in production.
- `VERCEL_TOKEN`, `VERCEL_TEAM_ID`
- `GITHUB_TOKEN`, `GITHUB_REPO`

## What the read-only role can and cannot do

It gets `SELECT` on every table and sequence in `public`, plus `USAGE` on the schema. It is
explicitly denied `CREATE` on the schema and `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE` on
every table, and the script verifies both facts after granting: if `can_select` is false or
`can_update` is true, the run fails instead of reporting success. It carries `BYPASSRLS`
because the tenant policies read a request-scoped setting that a plain SQL session never
sets, so without it every read would return zero rows; writes stay revoked, which is what
keeps that flag from becoming an isolation hole.

The password is generated by the script and printed once, to the operator, so it can be
handed over. It is never stored in this repository.

## Revocation order

Revoke in the order that closes the widest door first: platform role, then the Vercel
token, then the deploy key, then the SQL role. Then delete the engineer's user row and its
`OrganizationMember` row. Nothing here deletes a workspace or any data.
